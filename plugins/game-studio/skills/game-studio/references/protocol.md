# Studio protocol

This file is the contract between the producer and the roles. `studio_init.py` copies it
into the game project as `Studio/PROTOCOL.md`. All paths below are relative to the game
project root. Roles do not read this file on every run: their own prompt already holds
the rules they need. They open a section only when a question is not answered there.

## 1. Roles

| Role | Claude Code (`subagent_type`) | Codex (agent) |
|---|---|---|
| producer | main session, skill `game-studio` | main session, `$game-studio` |
| game-designer | `game-studio:game-designer` | `studio-game-designer` |
| art-director | `game-studio:art-director` | `studio-art-director` |
| architect | `game-studio:architect` | `studio-architect` |
| artist | `game-studio:artist` | `studio-artist` |
| developer | `game-studio:developer` | `studio-developer` |
| qa | `game-studio:qa` | `studio-qa` |
| sound-designer | `game-studio:sound-designer` | `studio-sound-designer` |
| narrative-designer | `game-studio:narrative-designer` | `studio-narrative-designer` |
| level-designer | `game-studio:level-designer` | `studio-level-designer` |

Every agent defaults to Sonnet with medium effort in Claude Code and to medium effort
in Codex. The producer picks the model and effort for each run from the routing table
(§14).

Only the producer talks to the user and writes the task board. Roles do not spawn other
agents and do not talk to each other directly. Everything one role hands to another goes
through files and through the producer.

## 2. Working language

`studio.json → language` holds the studio's working language as an ISO 639-1 code (`ru`,
`en`, …). The producer sets it at start from the language the user writes in. The
user can change it at any time. The producer passes it to every agent as `LANG`.

- Everything people read is written in `LANG`: documents, reports, reviews, summary
  text, TODO entries, bug reports, questions to the user.
- Machine-readable parts stay in English: summary field labels and `STATUS` values,
  task frontmatter keys, statuses, modes, file and folder names, JSON keys.
- Code, identifiers and code comments follow `Tech/ARCHITECTURE.md` (English by
  default).
- Player-facing text lives in `Narrative/strings/<LANG>.json` as the primary locale.
  Other locales come from the GDD.
- Templates are in English. When a role fills one in, it may translate the headings into
  `LANG`, except the ones tools read: the `##` headings of feature specs and the
  `## Summary` heading of reports.

## 4. `Studio/studio.json`

```json
{
  "version": 1,
  "game": "Title",
  "stack": "web-phaser | godot4 | unity | custom",
  "language": "en",
  "paths": {
    "art_export": "Art/export",
    "audio_export": "Audio/export",
    "levels_export": "Levels/export",
    "strings_export": "Narrative/strings",
    "code": ["src/**"],
    "unit_tests": ["tests/unit/**"],
    "acceptance_tests": ["tests/acceptance/**"],
    "project_files": ["package.json"]
  },
  "commands": {
    "setup": "", "run": "", "build": "", "test": "",
    "acceptance": "", "capture": "", "import_assets": ""
  },
  "zones": { "<role>": ["<glob>", "..."] },
  "shared_zones": ["Studio/reports/**/*.{role}.md", "..."],
  "producer_zones": ["Studio/tasks/**", "..."],
  "ignore": [".git", "node_modules", "..."],
  "limits": {
    "parallel_agents": 4, "features_per_sprint": 2,
    "rework_cycles": 3, "max_sprints": 5
  },
  "budget": {
    "profile": "standard",
    "max_agent_runs_per_sprint": 30, "max_tokens_per_sprint": 6000000,
    "meeting": "involved", "reviews": "batched", "reuse_reviewers": true,
    "reuse_max_context": 40000, "reuse_cold_max_context": 15000,
    "verify": "sprint-end", "tests_first": true
  },
  "git": { "auto_commit": false },
  "autopilot": false
}
```

- Globs: `**` matches any number of folders, `*` matches part of one name, no wildcard
  means an exact file.
- Zones support `${paths.<key>}`. A list value expands into one rule per element.
- `{role}` in `shared_zones` is replaced by the writing role. A shared rule without
  `{role}` applies to every role; use it for files an engine generates next to assets
  (`**/*.import`, `**/*.uid`, `**/*.meta`).
- `commands.capture` has `{scene}` and `{out}` placeholders and saves a PNG of that
  scene.

The architect fills `stack`, `paths`, `commands` and engine zones during
pre-production. Only the producer changes `language`, `limits`, `budget`, `git` and
`autopilot`, and only by the user's decision. A budget profile is applied with
`budget.py profile <name>` (§14).

## 5. Tasks

A task is `Studio/tasks/T-NNN.md`. Only the producer creates and changes tasks, via
`board.py`.

```markdown
---
id: T-007
title: Ship sprite and thrust animation
feature: F-001
sprint: 1
owner: artist
mode: WORK
status: todo
deps: [T-005]
reviewers: [art-director]
approvals: []
inputs: [Design/features/F-001-ship.md, References/Art Bible.md]
outputs: [Art/source/ship.sprite.json, Art/export/ship.png]
rework: 0
---

## Description
What to do and why, with links to spec sections.

## Done when
- checkable items

## Log
- S1 producer: created
```

Statuses: `todo` → `doing` → `review` → `done`. Side branches: `changes` (review sent
it back, `rework` +1) and `blocked` (waits for the user or an external fact).

A task is ready to work when its status is `todo` or `changes` and all `deps` are
`done`. A task in `review` waits for its `reviewers`. A task with no reviewers goes
straight to `done` after `DONE`.

### Feature task templates

The producer builds the tasks from the meeting and drops what the feature does not
need. The template depends on `budget.reviews`, `budget.verify` and
`budget.tests_first`.

**standard and thorough** (tests before code):

| # | Task | owner / mode | deps | reviewers |
|---|---|---|---|---|
| 1 | Tech plan F | architect / PLAN | — | — |
| 2 | Acceptance tests F | qa / WRITE_TESTS | 1 | — |
| 3 | Art F | artist / WORK | — | art-director |
| 4 | Sound F | sound-designer / WORK | — | game-designer |
| 5 | Text F | narrative-designer / WORK | — | game-designer |
| 6 | Levels F | level-designer / WORK | — | game-designer |
| 7 | Implement F | developer / WORK | 1, 2 | architect |
| 8 | Integrate assets F | developer / INTEGRATE | 3–7 | architect |

**lean** (tests after code, one review per feature):

| # | Task | owner / mode | deps | reviewers |
|---|---|---|---|---|
| 1 | Tech plan F | architect / PLAN | — | — |
| 2 | Assets F (sound, text, levels as separate tasks only if needed) | artist / WORK | — | — |
| 3 | Build F: implement and integrate | developer / WORK | 1, 2 | architect |

In lean the art is reviewed once per sprint by the art-director's `SCREEN_REVIEW`, and
the user sees it at the gate.

**Verification and acceptance:**
- `verify: sprint-end` (lean, standard): one task per sprint, `qa / VERIFY`, deps = the
  last developer task of every feature. Then one `game-designer / ACCEPT` per feature,
  deps = that verify task. In lean, VERIFY first writes the acceptance tests from the
  AC and the contract, then runs everything.
- `verify: per-feature` (thorough): per feature, `qa / VERIFY` (deps: tasks 7, 8), then
  `game-designer / ACCEPT` (deps: verify).

## 6. Agent prompt

The producer passes paths, never file contents. In a sprint `waves.py start` prints
these prompts ready to use:

```
PROJECT=<absolute path to the game project>
ROLE=<role>
MODE=<mode>
LANG=<language code>
PROFILE=<lean | standard | thorough>
SPRINT=<n>
TASKS=T-007[,T-008]                   (one task, or a batch of the same role and mode)
PACK=Studio/.state/packs/S<n>-W<k>-<role>.md
REPORT=<path, see SKILL.md>
CONTEXT: <paths: reviews, bug reports, meeting files, user answers, stack profile>
```

A batch is several tasks with the same role and mode in one run (`board.py next
--batch`). The agent does all of them, writes one report and gives each task its own
status in the summary.

The **pack** (`board.py pack`) is one file with what the run needs, so the agent does
not spend turns collecting it: the tasks with their description, done criteria and the
last log lines; the player story, the AC and the role's own section of each feature
spec (the whole spec for leads, developer and qa); the review section or bug report for
each task in rework; and the list of other inputs to open only if needed. Sections
are capped, and a cut ends with the `sed -n` range of the rest.

## 7. Role modes

| Role | Modes |
|---|---|
| game-designer | KICKOFF_TREE, PREPRO, SPEC, MEETING_RESOLVE, REVIEW, ACCEPT |
| architect | KICKOFF_TREE, PREPRO, MEETING, PLAN, CODE_REVIEW |
| art-director | PREPRO, MEETING, REVIEW, SCREEN_REVIEW |
| artist | PREPRO, MEETING, WORK, FIX |
| developer | WORK, INTEGRATE, FIX |
| qa | MEETING, WRITE_TESTS, VERIFY, FIX |
| sound-designer | PREPRO, MEETING, WORK, FIX |
| narrative-designer | PREPRO, MEETING, WORK, FIX |
| level-designer | PREPRO, MEETING, WORK, FIX |

`FIX` reworks a task after a review, a bug report or a test dispute. `CONTEXT` holds
the path to that review, bug or verdict. `MEETING` is a reply at the planning meeting
(§9).

## 8. Report and summary

The agent writes its report to `REPORT`, at most 60 lines: what was done, files, how it
was checked (command and condensed output), what is still doubtful. The report starts
with the summary, at most 15 lines in exactly this shape:

```
## Summary
STATUS: DONE | DONE_WITH_CONCERNS | NEEDS_INPUT | BLOCKED | APPROVE | CHANGES_REQUESTED | TEST_DISPUTE
TASK: T-NNN
FILES: path, path
CHECK: command → result in one line
HANDOFF: → <role>: <what to do or look at> (<paths>)
NEW TASKS: <owner>/<MODE>: <title> [deps: T-…] [reviewers: …]
QUESTIONS: <blocking only; each with a recommended answer>
```

For a batch, replace the first two lines with one line per task:
`T-007: DONE`, `T-008: CHANGES_REQUESTED — R-2, R-3`. Extra `NEW TASKS` or `QUESTIONS`
items go on their own `- ` lines under the label. A new task outside this sprint's
features gets `[later]` and lands in `Studio/proposals.md`. A task line may also carry
`[feature: F-…]`, `[inputs: …]`, `[outputs: …]`, `[done: a; b]` and `[desc: …]`.

Leave out empty lines. The labels stay in English; the text after them is in `LANG`.
`waves.py finish` reads the summary from the report and moves the board, so the agent's
final answer to the producer is one line: `<STATUS or per-task statuses> — <REPORT>`.
That keeps the producer's context from growing by a summary per run.
Status meanings:
- `DONE` means done and checked. `DONE_WITH_CONCERNS` means done with a doubt that the
  report explains.
- `NEEDS_INPUT` needs the user's answer. `BLOCKED` cannot continue without an external
  fact or another task.
- `APPROVE` and `CHANGES_REQUESTED` are the outcome of a review or acceptance.
- `TEST_DISPUTE`: the developer believes an acceptance test is wrong and leaves it
  untouched.

## 9. Handoffs and meetings

A **handoff** (`HANDOFF`) is an instruction for the next role. The producer writes it
to the task log as `S<n> <from> → <to>: <what>` and uses it to pick the next wave. If a
handoff needs new work, it goes to `NEW TASKS`.

**Sprint planning meeting** (`Studio/meetings/S<n>-planning/`), by `budget.meeting`:
- `none` (lean): no meeting. The game-designer's SPEC and the architect's PLAN carry
  the questions in their summaries.
- `involved` (standard): only the roles listed in the specs' "Roles needed", plus the
  architect.
- `full` (thorough): architect, qa, art-director and every content role the sprint
  touches.

The meeting itself:
1. game-designer (SPEC) writes or updates the specs of the sprint's features.
2. In parallel, each in its own `<role>.md`, at most 25 lines:
   ```
   ## What I need to do
   ## Risks and dependencies
   ## Questions to game-designer
   ## Proposed tasks
   - <owner>/<mode>: <title> [deps: …] [reviewers: …]
   ```
3. game-designer (MEETING_RESOLVE) answers the questions, updates specs and AC and writes
   its own `game-designer.md` with the decisions.
4. The producer writes `minutes.md` with the decisions and a `## Tasks` section of task
   lines. A line may carry `[id: <key>]` so that other lines name it in `deps`. Then
   `board.py import Studio/meetings/S<n>-planning/minutes.md` creates all the tasks at
   once; it creates nothing if a line is wrong.

## 10. Reviews and acceptance

| What | Made by | Reviewed by | Reviewer mode |
|---|---|---|---|
| Feature spec | game-designer | architect, qa at the meeting; user at the gate | MEETING |
| Art, mockups | artist | art-director | REVIEW |
| Game screenshots | taken by qa | art-director | SCREEN_REVIEW |
| Sound | sound-designer | game-designer | REVIEW |
| Text | narrative-designer | game-designer | REVIEW |
| Levels | level-designer | game-designer | REVIEW |
| Code | developer | architect | CODE_REVIEW |
| Whole feature | everyone | game-designer, after QA VERIFY | ACCEPT |

Review policy, by `budget.reviews`:
- `per-feature` (lean): code is reviewed once per feature on its Build task; art once
  per sprint through `SCREEN_REVIEW`.
- `batched` (standard): every task with reviewers is reviewed, but one reviewer run
  covers all of that reviewer's pending reviews in the wave.
- `every` (thorough): every task is reviewed in its own fresh run.

Reviews go to `Studio/reviews/<art|code>/T-NNN-r<k>.md`, or to one file per batch
(`Studio/reviews/<art|code>/S<n>-W<k>.md`) with a section per task. Findings are
numbered `R-1…` with a severity: 🔴 blocks, 🟡 must fix, 🟢 advice. The reviewer changes
nothing. Any 🔴 or 🟡 means `CHANGES_REQUESTED`.

A reviewer is never the author of the work. With `reuse_reviewers: true` the producer
may continue the same reviewer agent within a sprint (§14 says when); otherwise every
review is a fresh agent.

## 11. Write zones and the test lock

A role writes only to its zone from `studio.json` and its own files from
`shared_zones`. After every wave the producer runs `zones.py verify`. A write outside
the zone voids the round and is reverted. In Claude Code a hook also blocks such
writes.

After `WRITE_TESTS` (or the lean VERIFY that writes the tests) the producer locks the
acceptance tests with `zones.py lock`. If a locked test changes, the developer's round
is rejected. Only qa may change the tests, in a new cycle, and then the producer locks
them again.

## 12. Personal TODO lists

- `References/Art TODO.md` belongs to the artist: what to draw and redo, from mockups,
  reviews and specs, each with a link to its source. Closed items are marked `[x]` and
  kept.
- `References/Audio TODO.md` belongs to the sound-designer, same format.

## 13. Rules for everyone

- Stay inside the task. Another problem you found goes to `NEW TASKS`.
- Do not invent. An ambiguous requirement means `NEEDS_INPUT` with a recommended answer.
- "Done" needs proof: a command and its output, a path to a file or PNG.
- No commits, no pushes, no global installs.
- Write in `LANG`, briefly, one thought per sentence.

## 14. Token economy

The studio must ship the game without burning the budget. Quality comes from the
right checks at the right time, not from repeating them.

**Profiles.** The user picks one at kickoff; `budget.py profile <name>` writes it to
`studio.json`.

| | lean | standard | thorough |
|---|---|---|---|
| For | prototype, jam, ≤ 3 features | most games | long or risky projects |
| Meeting | none | involved roles | full |
| Reviews | per feature | batched per wave | every task, fresh |
| Tests | written by qa after the code | written by qa before the code | before the code |
| Full verification | once per sprint | once per sprint | per feature |
| Features per sprint | 1 | 2 | 2 |
| Rework rounds | 2 | 3 | 3 |
| Agent runs per sprint | 15 | 30 | 60 |
| Tokens per sprint (weighted, producer included) | 3M | 6M | 12M |
| Continue an agent up to this context | 40K | 40K | 60K |
| … once its cache has expired | 15K | 15K | 15K |

The token caps are a first estimate from comparable runs. After a real sprint, compare
them with `tokens.py report` and adjust `budget.max_tokens_per_sprint`.

**Model routing** (`budget.py route <role> <mode>` or `budget.py routes`):

| Work | lean | standard | thorough |
|---|---|---|---|
| Decisions: KICKOFF_TREE, SPEC, PLAN, ACCEPT, PREPRO of leads | Sonnet / medium | Opus / high | Opus / high |
| Reviews | Sonnet / medium | Sonnet / medium | Opus / high |
| Building: developer, qa, artist, MEETING_RESOLVE | Sonnet / medium | Sonnet / medium | Sonnet / high |
| Content: sound, narrative, levels | Haiku / low | Sonnet / medium | Sonnet / medium |
| MEETING replies | Haiku / low | Haiku / low | Sonnet / medium |

A task past its rework limit goes to Opus / high once. In Claude Code the producer
passes both the model and the effort to `Agent`; in Codex the effort.

**Where the tokens go.** Measured on comparable multi-agent runs:
- Every request of an agent re-sends what the agent started with. A Claude Code
  subagent that inherits the session's tools also inherits the list of every skill and
  MCP tool the user has: 21.9K tokens before the first word, against 7.6K with the
  explicit tool list the studio agents have. That start was 42–83% of all agent input.
- A Codex agent inherits the list of all the user's skills and, unless told otherwise,
  the whole conversation of the agent that spawned it. A probe role started at 29.7K
  tokens, and at 20.3K without the skill list.
- The producer was 32–72% of a session's spend. Every bookkeeping command is a request
  that re-sends the producer's whole context, which grows all session long.
- The prompt cache of a Claude Code subagent lives 5 minutes, and waves are longer. A
  continued agent whose cache has expired writes its whole context again at 1.25×.

So:
- **Agents** have an explicit tool list and medium effort and do not load `CLAUDE.md`
  (`scripts/build.py`); they never inherit the session's tools or effort. Codex roles
  switch off the skill list, connectors, plugins and memories, and the producer spawns
  them with `fork_turns: "none"`.
- **Packs** replace the turns an agent spends collecting its context (§6).
- **Waves** take two producer calls: `waves.py start` and `waves.py finish`. Agents answer
  in one line; the summary stays in the report, where `waves.py finish` reads it.
- **Continue an agent** only within the sprint, on the same model, and while its last
  context is at most `budget.reuse_max_context`. Once its cache has expired (5 minutes
  after its last request; 1 hour when the transcript shows 1-hour cache writes), only
  up to `budget.reuse_cold_max_context`. A continued agent re-sends its whole context on
  every request; past these limits a fresh agent with a pack is cheaper. `waves.py
  start` decides and prints `continue agent <id>` with the cache state, or `new agent`.

**Spend.** Tokens are weighted, input-equivalent tokens: input ×1, cache write ×1.25
(×2 for 1 h), cache read ×0.1, output ×5. Codex has no cache write price: its uncached
input counts ×1. `waves.py finish` reads each run's spend from its transcript (Claude
Code: by agent id; Codex: by the agent's name or thread id), and the producer's spend
since the last wave from the session transcript; it logs both with `budget.py log`.
The `subagent_tokens` figure of `Agent` is only the last request's size, not the spend;
pass it as `:<n>` only when there is no transcript. `waves.py start` stops with an
early gate when the next wave would pass the cap. `tokens.py report` shows the whole
session: producer, every run, the start prefix share, requests that found the cache
cold and files read more than once.

**Running commands.** Every project command goes through
`python3 Studio/tools/quiet.py "<command>"`. The full output lands in
`Studio/.state/logs/`; only the status line and the error lines reach the context. Open
a log only to read the part you need.

**Tests at the end.** Full test runs, the build and the screenshots happen once, in qa
VERIFY (per sprint in lean and standard). Before that:
- the developer runs only the tests of its own task: the unit tests it touched and the
  acceptance tests of its feature;
- the architect reviews the diff and does not rerun tests, except in thorough;
- qa runs the suite once; the second run against flaky tests happens only in thorough.

**Reading.** Read only what the task needs:
- in a feature spec: the player story, the AC and the section for your role;
- find headings with `grep -n '^## ' <file>` and read a range with `sed -n 'a,bp'`;
- never read lockfiles, logs in full, generated or binary files;
- look at one contact sheet instead of many PNGs; open a single PNG only when it is the
  thing under review.

**Writing.** Size limits: GDD ≤ 150 lines, feature spec ≤ 100, tech plan ≤ 120, Art
Bible ≤ 80, report ≤ 60, meeting reply ≤ 25, summary ≤ 15. A review lists findings only;
it does not retell the work.

**Stopping.** "Done when" is the finish line. No polishing beyond it, no checks that
another role owns.
