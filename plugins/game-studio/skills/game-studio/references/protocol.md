# Studio protocol

This file is the contract between the producer and the roles. `studio_init.py` copies it
into the game project as `Studio/PROTOCOL.md`. All paths below are relative to the game
project root.

## 1. Roles

| Role | Claude Code (`subagent_type`) | Codex (agent) | Tier |
|---|---|---|---|
| producer | main session, skill `game-studio` | main session, `$game-studio` | — |
| game-designer | `game-studio:game-designer` | `studio-game-designer` | lead |
| art-director | `game-studio:art-director` | `studio-art-director` | lead |
| architect | `game-studio:architect` | `studio-architect` | lead |
| artist | `game-studio:artist` | `studio-artist` | maker |
| developer | `game-studio:developer` | `studio-developer` | maker |
| qa | `game-studio:qa` | `studio-qa` | maker |
| sound-designer | `game-studio:sound-designer` | `studio-sound-designer` | maker |
| narrative-designer | `game-studio:narrative-designer` | `studio-narrative-designer` | maker |
| level-designer | `game-studio:level-designer` | `studio-level-designer` | maker |

Only the producer talks to the user and writes the task board. Roles do not spawn other
agents and do not talk to each other directly. Everything one role hands to another goes
through files and through the producer.

## 2. Working language

`studio.json → language` holds the studio's working language as an ISO 639-1 code (`ru`,
`en`, …). The producer sets it at start from the language the user writes in. The
user can change it at any time. The producer passes it to every agent as `LANG`.

- Everything people read is written in `LANG`: documents, reports, reviews, summary
  text, TODO entries, bug reports, questions to the user.
- Machine-readable parts stay in English: summary field labels and `STATUS` values,
  task frontmatter keys, statuses, modes, file and folder names, JSON keys.
- Code, identifiers and code comments follow `Tech/ARCHITECTURE.md` (English by
  default).
- Player-facing text lives in `Narrative/strings/<LANG>.json` as the primary locale.
  Other locales come from the GDD.
- Templates are in English. When a role fills one in, it may translate the headings into
  `LANG`.

## 4. `Studio/studio.json`

```json
{
  "version": 1,
  "game": "Title",
  "stack": "web-phaser | godot4 | unity | custom",
  "language": "en",
  "paths": {
    "art_export": "Art/export",
    "audio_export": "Audio/export",
    "levels_export": "Levels/export",
    "strings_export": "Narrative/strings",
    "code": ["src/**"],
    "unit_tests": ["tests/unit/**"],
    "acceptance_tests": ["tests/acceptance/**"],
    "project_files": ["package.json"]
  },
  "commands": {
    "setup": "", "run": "", "build": "", "test": "",
    "acceptance": "", "capture": "", "import_assets": ""
  },
  "zones": { "<role>": ["<glob>", "..."] },
  "shared_zones": ["Studio/reports/**/*.{role}.md", "..."],
  "producer_zones": ["Studio/tasks/**", "..."],
  "ignore": [".git", "node_modules", "..."],
  "limits": {
    "parallel_agents": 4, "features_per_sprint": 2,
    "rework_cycles": 3, "max_sprints": 5
  },
  "git": { "auto_commit": false },
  "autopilot": false
}
```

- Globs: `**` matches any number of folders, `*` matches part of one name, no wildcard
  means an exact file.
- Zones support `${paths.<key>}`. A list value expands into one rule per element.
- `{role}` in `shared_zones` is replaced by the writing role. A shared rule without
  `{role}` applies to every role; use it for files an engine generates next to assets
  (`**/*.import`, `**/*.uid`, `**/*.meta`).
- `commands.capture` has `{scene}` and `{out}` placeholders and saves a PNG of that
  scene.

The architect fills `stack`, `paths`, `commands` and engine zones during
pre-production. Only the producer changes `language`, `limits`, `git` and
`autopilot`, and only by the user's decision.

## 5. Tasks

A task is `Studio/tasks/T-NNN.md`. Only the producer creates and changes tasks, via
`board.py`.

```markdown
---
id: T-007
title: Ship sprite and thrust animation
feature: F-001
sprint: 1
owner: artist
mode: WORK
status: todo
deps: [T-005]
reviewers: [art-director]
approvals: []
inputs: [Design/features/F-001-ship.md, References/Art Bible.md]
outputs: [Art/source/ship.sprite.json, Art/export/ship.png]
rework: 0
---

## Description
What to do and why, with links to spec sections.

## Done when
- checkable items

## Log
- S1 producer: created
```

Statuses: `todo` → `doing` → `review` → `done`. Side branches: `changes` (review sent
it back, `rework` +1) and `blocked` (waits for the user or an external fact).

A task is ready to work when its status is `todo` or `changes` and all `deps` are
`done`. A task in `review` waits for its `reviewers`. A task with no reviewers goes
straight to `done` after `DONE`.

Feature task template. The producer builds it from the meeting and drops what the
feature does not need:

| # | Task | owner / mode | deps | reviewers |
|---|---|---|---|---|
| 1 | Tech plan F | architect / PLAN | — | — |
| 2 | Acceptance tests F | qa / WRITE_TESTS | 1 | — |
| 3 | Art F | artist / WORK | — | art-director |
| 4 | Sound F | sound-designer / WORK | — | game-designer |
| 5 | Text F | narrative-designer / WORK | — | game-designer |
| 6 | Levels F | level-designer / WORK | — | game-designer |
| 7 | Implement F | developer / WORK | 1, 2 | architect |
| 8 | Integrate assets F | developer / INTEGRATE | 3–7 | architect |
| 9 | Verify F | qa / VERIFY | 7, 8 | — |
| 10 | Accept F | game-designer / ACCEPT | 9 | — |

## 6. Agent prompt

The producer passes paths, never file contents:

```
PROJECT=<absolute path to the game project>
ROLE=<role>
MODE=<mode>
LANG=<language code>
SPRINT=<n>
TASK=Studio/tasks/T-NNN.md            (if any)
REPORT=Studio/reports/S<n>/T-NNN.<role>.md
CONTEXT: <paths: reviews, bug reports, meeting files, user answers, stack profile>
```

The agent first reads `Studio/PROTOCOL.md` (§2, §5–§13) and `TASK`. Then it reads the
task `inputs` and `Studio/studio.json`. Anything else only when needed.

## 7. Role modes

| Role | Modes |
|---|---|
| game-designer | KICKOFF_TREE, PREPRO, SPEC, MEETING_RESOLVE, REVIEW, ACCEPT |
| architect | KICKOFF_TREE, PREPRO, MEETING, PLAN, CODE_REVIEW |
| art-director | PREPRO, MEETING, REVIEW, SCREEN_REVIEW |
| artist | PREPRO, MEETING, WORK, FIX |
| developer | WORK, INTEGRATE, FIX |
| qa | MEETING, WRITE_TESTS, VERIFY, FIX |
| sound-designer | PREPRO, MEETING, WORK, FIX |
| narrative-designer | PREPRO, MEETING, WORK, FIX |
| level-designer | PREPRO, MEETING, WORK, FIX |

`FIX` reworks a task after a review, a bug report or a test dispute. `CONTEXT` holds
the path to that review, bug or verdict. `MEETING` is a reply at the planning meeting
(§9).

## 8. Report and summary

The agent writes its full report to `REPORT`: what was done, files, how it was checked
(command and condensed output), what is still doubtful.

The summary for the producer is at most 15 lines in exactly this shape:

```
STATUS: DONE | DONE_WITH_CONCERNS | NEEDS_INPUT | BLOCKED | APPROVE | CHANGES_REQUESTED | TEST_DISPUTE
TASK: T-NNN
FILES: path, path
CHECK: command → result in one line
HANDOFF: → <role>: <what to do or look at> (<paths>)
NEW TASKS: <owner>/<mode>: <title> [deps: T-…] [reviewers: …]
QUESTIONS: <blocking only; each with a recommended answer>
```

Leave out empty lines. The labels stay in English; the text after them is in `LANG`.
Status meanings:
- `DONE` means done and checked. `DONE_WITH_CONCERNS` means done with a doubt that the
  report explains.
- `NEEDS_INPUT` needs the user's answer. `BLOCKED` cannot continue without an external
  fact or another task.
- `APPROVE` and `CHANGES_REQUESTED` are the outcome of a review or acceptance.
- `TEST_DISPUTE`: the developer believes an acceptance test is wrong and leaves it
  untouched.

## 9. Handoffs and meetings

A **handoff** (`HANDOFF`) is an instruction for the next role. The producer writes it
to the task log as `S<n> <from> → <to>: <what>` and uses it to pick the next wave. If a
handoff needs new work, it goes to `NEW TASKS`.

**Sprint planning meeting** (`Studio/meetings/S<n>-planning/`):
1. game-designer (SPEC) writes or updates the specs of the sprint's features.
2. In parallel, each in its own `<role>.md`: architect, artist, sound-designer,
   narrative-designer, level-designer, qa and art-director (when the sprint brings new
   visual content). Reply format:
   ```
   ## What I need to do
   ## Risks and dependencies
   ## Questions to game-designer
   ## Proposed tasks
   - <owner>/<mode>: <title> [deps: …] [reviewers: …]
   ```
   A role the feature does not concern answers with one line: "Not involved: <why>".
3. game-designer (MEETING_RESOLVE) answers the questions, updates specs and AC and writes
   its own `game-designer.md` with the decisions.
4. The producer writes `minutes.md` with decisions, tasks and dependencies, and creates
   tasks from it.

## 10. Reviews and acceptance

| What | Made by | Reviewed by | Reviewer mode |
|---|---|---|---|
| Feature spec | game-designer | architect, qa at the meeting; user at the gate | MEETING |
| Art, mockups | artist | art-director | REVIEW |
| Game screenshots | taken by qa | art-director | SCREEN_REVIEW |
| Sound | sound-designer | game-designer | REVIEW |
| Text | narrative-designer | game-designer | REVIEW |
| Levels | level-designer | game-designer | REVIEW |
| Code | developer | architect | CODE_REVIEW |
| Whole feature | everyone | game-designer, after QA VERIFY | ACCEPT |

Reviews go to `Studio/reviews/<art|code>/T-NNN-r<k>.md` or to the reviewer's report.
Findings are numbered `R-1…` with a severity: 🔴 blocks, 🟡 must fix, 🟢 advice. The
reviewer changes nothing. Any 🔴 or 🟡 means `CHANGES_REQUESTED`.

Reviewers and acceptance always run as fresh agents without the author's history.

## 11. Write zones and the test lock

A role writes only to its zone from `studio.json` and its own files from
`shared_zones`. After every wave the producer runs `zones.py verify`. A write outside
the zone voids the round and is reverted. In Claude Code a hook also blocks such
writes.

After `WRITE_TESTS` the producer locks the acceptance tests with `zones.py lock`. If a
locked test changes, the developer's round is rejected. Only qa may change the tests,
in a new cycle, and then the producer locks them again.

## 12. Personal TODO lists

- `References/Art TODO.md` belongs to the artist: what to draw and redo, from mockups,
  reviews and specs, each with a link to its source. Closed items are marked `[x]` and
  kept.
- `References/Audio TODO.md` belongs to the sound-designer, same format.

## 13. Rules for everyone

- Stay inside the task. Another problem you found goes to `NEW TASKS`.
- Do not invent. An ambiguous requirement means `NEEDS_INPUT` with a recommended answer.
- "Done" needs proof: a command and its output, a path to a file or PNG.
- No commits, no pushes, no global installs.
- Write in `LANG`, briefly, one thought per sentence.
